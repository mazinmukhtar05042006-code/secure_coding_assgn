📋 Recommended Security Fix Order (Required Priority Breakdown)

01 CRITICAL RISK • FIX IMMEDIATELY
OS Command Injection

Why First: Direct arbitrary OS command execution leads to total host takeover, ransomware, and server control.

Secure Fix: Strict allowlist validation + subprocess.run(["cmd", arg], shell=False).
Principles: Minimize Attack Surface, Input Validation, Defense in Depth, Least Privilege.
View detailed justification

Raw input directly reached the shell interpreter. Because an attacker can run commands with the application's privileges, this poses the single highest threat to system integrity and confidentiality.

02 CRITICAL RISK • FIX IMMEDIATELY
Plaintext Password Storage

Why Second: Database or backup leaks instantly compromise all accounts; credential stuffing impacts external services.

Secure Fix: Salted password hashing (PBKDF2/scrypt) + constant-time verification.
Principles: Secure Data Handling, Defense in Depth, Least Privilege.
View detailed justification

Storing passwords in cleartext guarantees total identity loss upon any storage exposure. Applying cryptographic salted key derivation protects credentials at rest even if the database is stolen.

03 HIGH RISK • FIX NEXT
File Path Traversal

Why Third: Allows reading unauthorized files outside web root, leaking application source, keys, and OS configurations.

Secure Fix: Path canonicalization via Path.resolve() + base directory containment check.
Principles: Complete Mediation, Minimize Attack Surface, Secure by Default.
View detailed justification

Relative traversal tokens (../) bypass naive string concatenation. Resolving the canonical absolute path ensures complete mediation before any file descriptor is opened.

04 HIGH RISK • FIX NEXT
Unmanaged External Dependencies

Why Fourth: Third-party libraries introduce inherited supply-chain CVEs easily weaponized by automated botnets.

Secure Fix: Minimal requirements.txt, version pinning, and automated SCA (pip-audit).
Principles: Minimize Attack Surface, Defense in Depth, Secure Recovery.
View detailed justification

Applications inherit vulnerabilities from deep transitive dependency trees. Establishing a minimal package manifest and automated vulnerability scans eliminates known public exploits.

05 MEDIUM RISK • FOLLOW-UP
Predictable Temporary Files

Why Fifth: Static names cause symlink hijacking and race conditions in shared/multi-user environments.

Secure Fix: Use tempfile.NamedTemporaryFile with cryptographically random names & auto-cleanup.
Principles: Secure by Default, Minimize Attack Surface, Secure Data Handling.
View detailed justification

Exploitation requires local presence or shared execution space. While serious, it ranks below direct remote RCE and credential exposure.

06 MEDIUM RISK • FOLLOW-UP
Improper Exception Handling

Why Sixth: Stack traces disclose internal paths and software versions, aiding attacker reconnaissance.

Secure Fix: Catch specific exceptions, return sanitized user errors, and log diagnostics server-side.
Principles: Fail Securely, Secure Data Handling, Defense in Depth.
View detailed justification

Information disclosure assists attacker reconnaissance rather than granting immediate remote execution, making it a follow-up remediation.

⚖️ Prioritization Methodology & Risk Formula
Risk = Likelihood × Impact

Implementation priority is based on the combination of likelihood and potential impact. Vulnerabilities with the greatest potential to compromise confidentiality, integrity, or availability and/or enable direct remote compromise are addressed earlier. Medium-risk weaknesses are still required to be fixed, but are addressed after higher-risk issues.
