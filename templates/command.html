Vulnerability 1 CRITICAL RISK

Command Injection

Direct use of unvalidated user input in system commands allows attackers to execute arbitrary shell operations.

⚠️ SECTION B: What Went Wrong?
  • Raw Concatenation: Untrusted user input was stitched directly into the system command string.
  • Shell Interpretation: Using shell=True passes the string to cmd.exe or sh, which parses metacharacters (&, ;, |).
  • No Validation: The application failed to enforce an allowlist or verify that the input was strictly an IP address.
⚖️ SECTION D: Before vs After Fix
❌ Vulnerable Approach
❌ Raw string concatenation
❌ shell=True enabled
❌ No input format validation
❌ Arbitrary shell commands possible
✓ Secure Implementation
✓ Server-side allowlist validation (Regex/IP)
✓ Structured argument vector (list)
✓ shell=False (direct OS process)
✓ Zero shell metacharacter parsing
🎯 SECTION E: Secure Coding Principle

Defense in Depth & Least Privilege: Combine server-side allowlist validation with structured process argument vectors so that even if input validation misses an edge-case token, the execution engine cannot invoke a shell interpreter.

Why does this matter in real systems?

Command injection is ranked among the highest-severity flaws (CWE-78 / OWASP Top 10) because it directly leads to Remote Code Execution (RCE), allowing adversaries to pivot into local networks, download ransomware, or exfiltrate databases.
